# 恒生数据API技能异常处理设计文档

## 1. 引言

### 1.1 目标
为恒生数据API技能提供完善的异常处理机制，提升技能的健壮性和用户体验，确保在各种错误场景下都能提供明确的反馈和恢复建议。

### 1.2 原则
1. **用户友好**：错误提示应当清晰易懂，避免暴露内部实现细节
2. **完整性**：覆盖所有可能出现的错误场景，包括网络、API、数据、参数等
3. **可恢复性**：对临时性错误（如网络波动）提供自动重试机制
4. **可排查性**：记录详细的错误日志，便于问题诊断和修复
5. **一致性**：统一的异常处理流程和错误信息格式

## 2. 异常类层次结构

### 2.1 基础异常类
```
HSDataError (基础异常类)
├── LicenceError (许可证相关错误，401)
├── RateLimitError (请求频率超限，403)
├── DataNotFoundError (数据不存在，404)
├── APIError (API服务器错误，500/502/503等)
├── NetworkError (网络连接错误)
├── ParameterError (参数错误)
└── FormatError (数据格式错误)
```

### 2.2 异常类说明
| 异常类 | HTTP状态码 | 触发场景 | 用户提示示例 |
|--------|-----------|----------|-------------|
| LicenceError | 401 | 许可证无效、过期或无权访问 | "许可证无效或已过期，请检查您的许可证" |
| RateLimitError | 403 | 请求频率超限 | "请求频率超限，请稍后再试" |
| DataNotFoundError | 404 | 股票代码不存在、接口不存在 | "未找到股票代码'000001'对应的数据" |
| APIError | 500/502/503 | 服务器内部错误、网关错误 | "服务器暂时不可用，请稍后重试" |
| NetworkError | N/A | 网络连接超时、DNS解析失败 | "网络连接异常，请检查网络后重试" |
| ParameterError | N/A | 缺少必要参数、参数格式错误 | "缺少必要参数：symbol" |
| FormatError | N/A | JSON解析失败、数据格式异常 | "数据格式解析失败，请稍后重试" |

## 3. 常见错误场景分析

### 3.1 许可证相关错误
1. **许可证无效**：许可证格式错误、已被吊销
2. **许可证过期**：许可证超过有效期
3. **无权访问**：许可证无权访问特定数据模块

### 3.2 网络相关错误
1. **连接超时**：服务器响应超时
2. **连接拒绝**：服务器拒绝连接
3. **DNS解析失败**：无法解析API域名
4. **SSL证书错误**：HTTPS证书验证失败

### 3.3 API服务器错误
1. **服务器内部错误** (500)：服务器处理请求时出错
2. **网关错误** (502/503)：负载均衡或代理服务器错误
3. **服务不可用** (503)：服务器维护或过载

### 3.4 请求限制错误
1. **频率限制**：单位时间内请求次数超限
2. **配额用尽**：月度或总请求配额用尽
3. **并发限制**：同时连接数超限

### 3.5 数据相关错误
1. **股票代码不存在**：输入的股票代码无效
2. **日期范围无效**：开始日期晚于结束日期
3. **数据不存在**：请求的数据在指定时间范围内不存在
4. **字段不存在**：请求的字段在当前数据模块中不存在

### 3.6 参数相关错误
1. **缺少必要参数**：未提供必需参数
2. **参数格式错误**：日期格式、代码格式不正确
3. **参数值越界**：数值参数超出有效范围
4. **参数类型错误**：参数类型不符合预期

## 4. 错误处理流程设计

### 4.1 整体流程
```
用户请求 → 参数验证 → API调用 → 响应处理 → 结果返回
      ↓           ↓         ↓           ↓
   参数错误    参数错误  网络/API错误 格式错误
```

### 4.2 错误处理层级
1. **参数验证层**：在`query()`方法中验证模块、操作、输出格式
2. **模块验证层**：在`_get_module()`中验证模块名称有效性
3. **请求构建层**：在`_build_url()`中验证参数完整性和格式
4. **HTTP请求层**：在`_request()`中处理网络和HTTP错误
5. **响应解析层**：在`_request()`中解析JSON和检查API错误
6. **数据格式化层**：在格式化器中处理数据转换错误

### 4.3 错误传播机制
1. 底层异常应尽可能转换为具体的`HSDataError`子类
2. 未处理的异常应被捕获并转换为`HSDataError`，避免暴露堆栈信息
3. 保留原始异常信息到日志中，便于调试

## 5. 重试机制设计

### 5.1 重试策略
1. **适用场景**：网络超时、连接错误、服务器临时错误(502/503)
2. **不重试场景**：参数错误、许可证错误、数据不存在(404)、频率限制(403)

### 5.2 重试配置
```python
REQUEST_CONFIG = {
    "timeout": 30,           # 单次请求超时时间（秒）
    "max_retries": 3,        # 最大重试次数
    "retry_delay": 1,        # 重试延迟（秒），可考虑指数退避
    "retry_status_codes": [502, 503, 504],  # 需要重试的状态码
}
```

### 5.3 重试实现
1. 在`_request()`方法中实现递归重试
2. 对`requests.exceptions.Timeout`和`requests.exceptions.ConnectionError`自动重试
3. 对特定HTTP状态码（502/503）进行重试
4. 重试时增加延迟，避免加重服务器负担

## 6. 用户友好提示设计

### 6.1 提示信息结构
```
[错误类型] 错误描述

可能的原因：
• 原因1
• 原因2

建议的解决方案：
1. 解决方案1
2. 解决方案2

如需帮助，请提供以下信息给技术支持：
• 错误代码：[code]
• 请求模块：[module]
• 时间戳：[timestamp]
```

### 6.2 各场景提示示例
1. **网络错误**：提供网络检查建议和重试提示
2. **许可证错误**：提示检查许可证有效期和格式
3. **参数错误**：明确指出哪个参数有问题，提供正确格式示例
4. **数据不存在**：建议检查股票代码或日期范围
5. **服务器错误**：提示稍后重试，避免立即重复请求

### 6.3 本地化考虑
错误信息使用中文，符合用户交流语言要求。

## 7. 日志记录策略

### 7.1 日志级别
- **DEBUG**：详细的请求/响应信息，用于开发调试
- **INFO**：正常操作记录，如API调用开始结束
- **WARNING**：非关键错误，如重试发生
- **ERROR**：关键错误，需要人工干预
- **CRITICAL**：系统级错误，如许可证完全失效

### 7.2 日志内容
```python
{
    "timestamp": "2024-01-01T12:00:00",
    "level": "ERROR",
    "module": "stock_list",
    "action": "get_list",
    "error_code": 401,
    "error_message": "许可证无效",
    "request_params": {...},
    "response_content": "...",
    "retry_count": 2,
    "user_id": "optional",
    "traceback": "..."  # 仅开发环境
}
```

### 7.3 日志输出
1. 控制台输出（开发环境）
2. 文件输出（生产环境），按日期分割
3. 敏感信息脱敏（如许可证部分掩码）

## 8. 集成到现有代码

### 8.1 需要增强的模块
1. **core.py** `query()`方法：增强异常捕获和转换
2. **base.py** `_request()`方法：完善重试逻辑和错误映射
3. **exceptions.py**：补充更多具体的异常子类
4. **config.py**：增加错误代码映射和重试配置

### 8.2 具体修改点
1. 在`query()`方法中添加更细致的异常处理，确保所有异常都被转换为用户友好格式
2. 在`_request()`方法中增加对API返回错误信息的解析
3. 为常见错误场景定义具体的异常类，如`StockCodeError`、`DateRangeError`等
4. 增加请求ID和跟踪机制，便于问题排查

### 8.3 向后兼容性
所有修改保持向后兼容，现有API接口和行为不变。

## 9. 测试策略

### 9.1 单元测试
覆盖所有异常场景：
1. 模拟网络超时、连接错误
2. 模拟各种HTTP状态码返回
3. 模拟无效参数输入
4. 模拟API返回错误信息

### 9.2 集成测试
1. 真实API调用，验证错误处理流程
2. 模拟高并发场景，测试重试机制
3. 长期运行测试，验证稳定性

### 9.3 测试工具
使用`unittest.mock`模拟网络响应，`pytest`组织测试用例。

## 10. 部署和维护

### 10.1 监控指标
1. 错误率：各类错误的发生频率
2. 重试率：需要重试的请求比例
3. 平均响应时间：正常和异常场景
4. 许可证使用情况：有效、过期、无效统计

### 10.2 告警机制
1. 错误率超过阈值（如5%）
2. 许可证大规模失效
3. API服务不可用超过一定时间

### 10.3 维护流程
1. 定期更新错误代码映射
2. 根据用户反馈优化提示信息
3. 监控日志，发现潜在问题
